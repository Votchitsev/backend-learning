# Don't Block the Event Loop (or the Worker Pool)

Первоисточник: [Don't Block the Event Loop (or the Worker Pool)](https://nodejs.org/en/learn/asynchronous-work/dont-block-the-event-loop). Сверено 14.10.2026; примеры и терминология соотнесены с Node.js v24.21.0 LTS.

## Should you read this guide? / Summary

Для сервера важна длительность работы на каждого клиента. Node.js обслуживает много клиентов небольшим числом threads; если один из них долго занят одним запросом, остальные ждут. Это влияет и на throughput, и на доступность сервиса.

## Why should I avoid blocking the Event Loop and the Worker Pool?

Долгий callback на Event Loop задерживает **всех** клиентов, чьи callbacks готовы. Долгая задача в Worker Pool занимает один из ограниченного числа workers и задерживает задачи в очереди. Ввод, вынуждающий сервер долго работать, может превратиться в denial of service.

## A quick review of Node

### What code runs on the Event Loop?

Первоначальная инициализация и JavaScript callbacks выполняются на Event Loop. Сюда возвращаются callbacks завершившихся асинхронных операций. Сетевой I/O обычно использует неблокирующие механизмы ОС; ожидание сети не означает выделение worker каждому запросу.

### What code runs on the Worker Pool?

libuv Worker Pool выполняет задачи, для которых полезен отдельный thread: асинхронные файловые операции, `dns.lookup` и `dns.lookupService`, некоторые `crypto` операции (`pbkdf2`, `scrypt`, `randomBytes`, `randomFill`, `generateKeyPair`) и асинхронные `zlib` операции. Не всякая асинхронная операция использует этот пул. JavaScript callback результата всё равно исполняется на Event Loop.

### How does Node.js decide what code to run next?

Event Loop реагирует на готовность I/O через системные механизмы вроде epoll, kqueue или IOCP и на завершение задач Worker Pool. У пула есть очередь задач. Представление об «одной общей очереди callbacks» полезно лишь как упрощение: разные источники работы имеют разные правила обработки.

### What does this mean for application design?

Когда один thread обслуживает многих клиентов, fairness зависит от длительности каждого callback и worker task. Ограничивайте объём входных данных и время вычислений; измеряйте хвост задержек, а не только среднее.

## Don't block the Event Loop

### How careful should you be?

Оценивайте сложность операции по размеру пользовательского ввода. Даже линейный алгоритм может быть опасен при огромном `n`. Устанавливайте пределы размеров и проверяйте худший допустимый случай.

### REDOS

Регулярное выражение с катастрофическим backtracking может обрабатывать специально подобранную строку экспоненциально долго. Валидация таких строк на Event Loop остановит ответы другим клиентам. Ограничение ввода и безопасная конструкция выражения важнее того, что regexp выглядит коротким.

### Node.js core modules

Синхронные варианты дорогих API, особенно `fs`, `crypto`, `zlib` и некоторые операции с процессами, выполняют работу на Event Loop и задерживают другие callbacks. Асинхронная версия может убрать ожидание с Event Loop, но её worker task тоже имеет стоимость.

### JSON DOS

`JSON.parse` и `JSON.stringify` синхронны. Большой вложенный объект или строка могут удерживать Event Loop заметное время. Проверяйте размер входных данных и выбирайте способ обработки больших данных осознанно.

### Complex calculations without blocking the Event Loop

**Partitioning** делит вычисление на короткие шаги, между которыми Event Loop может обслужить другие события. **Offloading** выполняет расчёт вне Event Loop, например через подходящий worker механизм. Простая обёртка `Promise.resolve().then(() => heavyWork())` не переносит `heavyWork` в другой thread. Статья показывает обе стратегии; выбор зависит от стоимости задачи и накладных расходов.

## Don't block the Worker Pool

### Minimizing the variation in Task times

Если одни worker tasks занимают миллисекунды, а другие секунды, короткие задачи могут стоять за длинными. Ограничивайте размер каждой задачи и следите за разбросом длительности, а не только за средним.

### Task partitioning

Большую задачу можно делить на части, чтобы workers регулярно освобождались для работы других клиентов. Каждая часть добавляет накладные расходы, поэтому гранулярность выбирают измерением.

### Avoiding Task partitioning

Для некоторых задач разумнее ограничить входные данные или использовать отдельные ресурсы, чем вручную дробить работу. Обход блокировки не должен нарушать семантику операции.

### Conclusions / The risks of npm modules / Conclusion

Фактически исполняемый код зависит и от библиотек: модуль может скрывать дорогую синхронную работу или неограниченный ввод. Проверяйте поведение зависимостей под нагрузкой. Общий вывод статьи: короткие callbacks и ограниченные worker tasks позволяют небольшому числу threads справедливо обслуживать множество клиентов.
